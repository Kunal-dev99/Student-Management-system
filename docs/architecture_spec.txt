1.	System	overview
The	platform	manages	the	full	relationship	between	a	person	and	the	institution,	from	a	research	opportunity	through
recruitment,	registration,	progression,	funding,	thesis,	examination,	completion,	and	alumni	status.	It	integrates	with
Research,	Finance,	and	HR	systems	rather	than	replacing	them.
The	central	object	is	not	the	student.	It	is	the	person,	tracked	across	every	identity	the	person	can	hold	over	time.
Person	->	Research	Opportunity	->	Application	->	Research	Student	->
Research	Journey	->	Funding	->	Progression	->	Thesis	->	Outcome	->
Alumni	/ 	Employee	/ 	Researcher
Funding	is	modelled	as	a	cross	cutting	dimension,	not	a	single	stage,	because	a	person	can	move	between	funding
arrangements	during	one	research	journey.
The	system	owns	the	PGR	lifecycle	and	the	workflow	around	it.	It	does	not	own	payroll,	general	ledger,	research	grant
administration,	or	bulk	document	storage.	Those	remain	in	the	systems	of	record	and	are	reached	through	integration
adapters.
===== PAGE 7 =====
2.	Architecture	goals	and	principles
Goals:
1.	
Model	the	person	once	and	preserve	one	identity	across	applicant,	student,	employee,	and	alumni	states.
2.	
Make	the	lifecycle	configurable,	so	milestones,	workflows,	and	assessment	criteria	can	differ	by	institution	and
programme	without	code	changes.
3.	
Keep	external	systems	of	record	authoritative	and	integrate	through	clear	boundaries.
4.	
Scale	horizontally	on	the	API	and	worker	tiers,	with	the	database	tuned	for	read	heavy	reporting.
5.	
Produce	a	full	and	defensible	audit	trail	for	every	academic	and	funding	decision.
Principles:
Modular	monolith	first.	The	backend	is	one	deployable	FastAPI	application	split	into	strict	domain	modules	with
private	internals.	Modules	can	be	extracted	into	separate	services	later	without	rewriting	business	logic,	because
each	module	already	talks	to	others	through	service	interfaces	and	domain	events,	not	shared	tables.
Layered	inside	each	module:	API	layer,	service	layer	(business	rules),	repository	layer	(data	access),	domain	models.
No	layer	reaches	around	the	one	below	it.
Explicit	contracts.	Pydantic	schemas	define	every	request	and	response.	SQLAlchemy	models	never	leak	to	the	API
layer.
Async	by	default	for	input	and	output	bound	work.	CPU	bound	or	long	running	work	goes	to	background	workers.
Configuration	over	hard	coding.	Lifecycle	rules	live	in	data,	not	in	branches.
Fail	closed	on	authorization.	A	request	with	no	matching	permission	is	denied.

3.2	Container	responsibilities
React	SPA:	presentation,	client	routing,	role	aware	views.	Talks	only	to	the	API	over	HTTPS.
API	tier:	stateless	FastAPI	pods.	Handles	synchronous	requests,	validation,	authorization,	and	orchestration	of
services.	Emits	domain	events	to	the	outbox.
Worker	tier:	consumes	tasks	and	scheduled	jobs.	Runs	notifications,	milestone	generation,	funding	expiry	checks,
integration	sync,	and	report	refresh.
PostgreSQL:	transactional	store.	Primary	for	writes,	one	or	more	read	replicas	for	reporting	and	dashboards.
Redis:	response	cache,	rate	limiter	store,	and	short	lived	task	broker	for	ARQ	if	chosen.
Object	store:	thesis	files	and	evidence	documents	by	reference.	Large	document	management	can	also	stay
external.
Message	broker:	reliable	delivery	of	domain	events	to	the	integration	hub	and	between	modules	if	they	are	later
split.

6.	Backend	architecture
6.1	Layering
HTTP	request
			->	Router	(validation	via	Pydantic,	authz	dependency)
						->	Service	(business	rules,	transactions,	events)
									->	Repository	(SQLAlchemy	queries)
												->	Database
						<-	Domain	object	mapped	to	response	schema
			<-	JSON	response
Rules:
Routers	contain	no	business	logic.	They	validate	input,	resolve	the	current	user,	call	a	service	method,	and	shape	the
response.
Services	own	transactions.	A	service	method	opens	a	unit	of	work,	calls	one	or	more	repositories,	writes	any	domain
events	to	the	outbox	in	the	same	transaction,	then	commits.
Repositories	contain	queries	only.	They	return	domain	objects	or	plain	rows,	never	HTTP	concerns.
Cross	module	calls	go	service	to	service.	If	
admissions
	needs	a	person,	it	calls	
person_service.get_or_create
,	not	the
person	tables.
6.2	Request	lifecycle	and	middleware
Order	of	processing:
1.	
TLS	ends	at	the	ingress.	The	API	sees	plain	HTTP	inside	the	cluster.
2.	
Middleware	attaches	a	request	id,	starts	a	trace	span,	and	records	start	time.
3.	
Authentication	dependency	validates	the	JWT	and	loads	the	principal.
4.	
Authorization	dependency	checks	the	required	permission	and	applies	row	scoping.
5.	
The	route	handler	runs,	calls	the	service,	and	returns	a	Pydantic	model.
6.	
Exception	handlers	convert	known	errors	to	the	standard	error	envelope.
7.	
Middleware	logs	method,	path,	status,	duration,	and	request	id	as	one	structured	line.
6.3	Configuration
All	configuration	comes	from	environment	variables,	loaded	once	into	a	typed	settings	object.	No	secrets	in	code.	Local
development	uses	
.env
.	Clusters	use	secrets	and	config	maps.	See	Appendix	C	for	the	variable	list.
6.4	Error	handling
One	exception	hierarchy	in	
core/ errors.py
:
AppError
	base	with	
code
,	
message
,	
http_status
.
NotFoundError
,	
ConflictError
,	
ValidationAppError
,	
AuthError
,	
PermissionError
,	
IntegrationError
,	
WorkflowError
.
A	single	handler	renders	the	standard	envelope	in	Appendix	B.	Unhandled	exceptions	return	a	generic	500	with	a	request	id
and	never	leak	internals.
6.5	Dependency	injection
FastAPI	dependencies	provide	the	database	session,	the	current	principal,	and	the	permission	guard.	Services	receive	their
repositories	through	constructor	injection	in	tests	and	through	a	small	factory	in	the	app,	so	units	can	be	tested	without	a
database.

8.	Data	model	(PostgreSQL)
8.1	Conventions
UUID	primary	keys	named	
id
.
Foreign	keys	named	
<entity>_id
.
Status	columns	use	PostgreSQL	enum	types	or	a	constrained	text	with	a	check.
Timestamps	
created_at
,	
updated_at
	default	to	
now()
	at	UTC.	
updated_at
	maintained	by	a	trigger.
Soft	delete	only	where	history	matters,	using	
deleted_at
.	Most	lifecycle	records	are	never	hard	deleted.

9.	Workflow,	task,	and	notification	engine
Almost	every	lifecycle	event	creates	work	for	a	person.	The	platform	ships	one	reusable	engine	rather	than	hard	coding	each
flow.
9.1	Model
workflow_definition								#	a	named	state	machine,	versioned
		states:	[	...	]
		transitions:	[	{from,	to,	on_event,	guard,	actions}	]
workflow_instance										#	a	running	flow	bound	to	an	aggregate
		definition_id,	aggregate_type,	aggregate_id,	current_state,	context	jsonb
task																							#	a	unit	of	human	work
		workflow_instance_id,	assignee_role	or	assignee_user_id,
		title,	due_at,	status,	payload	jsonb
notification															#	an	outbound	message
		recipient_user_id,	channel,	template,	payload,	status
9.2	Triggers
Events	raise	transitions.	Examples:
offer.accepted
	starts	the	onboarding	workflow	and	creates	onboarding	tasks.
milestone.due
	notifies	student	and	supervisor	and	opens	a	review	task.
thesis.submitted
	creates	the	examiner	nomination	workflow.
funding.expiring_90d
	notifies	the	administrator	to	plan	renewal.
progression.failed
	opens	the	decision	workflow.
9.3	Timers	and	scheduled	jobs
A	scheduled	worker	runs	periodic	checks:
generate	milestones	that	fall	due	from	
milestone_definition
.
flag	funding	arrangements	expiring	within	90	days.
escalate	tasks	past	their	due	date.
refresh	reporting	materialized	views.
9.4	Guarantees
Task	creation	and	the	triggering	state	change	happen	in	one	database	transaction.	Notifications	are	queued	through	the
outbox	so	a	broker	outage	never	loses	a	message.	Delivery	is	at	least	once,	and	templates	are	idempotent	by	notification	id.

10.2	Patterns
Anti	corruption	layer.	Each	adapter	translates	external	shapes	into	platform	domain	terms,	so	external	changes	do

Outbox	and	dispatcher.	Domain	events	are	written	to

12.	Authentication,	authorization,	RBAC,	and	audit
12.1	Authentication
Primary	path	is	OIDC	against	the	institutional	identity	provider.	The	platform	validates	the	token,	maps	identity
provider	groups	to	platform	roles,	and	issues	its	own	short	lived	access	token	plus	a	refresh	token.
A	local	password	path	exists	for	service	accounts	and	non	SSO	users.	Passwords	are	hashed	with	a	strong	algorithm.
Access	tokens	are	short	lived.	Refresh	tokens	are	stored	hashed	and	can	be	revoked.
12.2	Authorization	model
Role	based	access	with	fine	grained	permissions	and	row	scoping.
permission					#	verb	on	a	resource,	for	example	student.read,	funding.change
role											#	a	named	set	of	permissions
role_permission
user_role
Roles	from	the	blueprint,	each	with	a	default	permission	set:
Student:	own	journey	read,	own	submissions	write.
Supervisor:	read	and	act	on	own	supervisees	only.
PGR	Administrator:	manage	lifecycle	across	the	assigned	unit.
Academic	or	Panel:	assess	progression.
Admissions	or	Recruitment:	manage	applications.
Research	Office:	read	research	and	funding	relationships.
Finance:	read	funding	and	stipend	relationships.
HR:	read	relevant	person	and	workforce	relationship.
Registry:	manage	registration,	completion,	and	statutory	data.
Institution	Administrator:	configure	programmes,	workflows,	and	rules.
Executive:	read	only	enterprise	analytics.
12.3	Row	scoping
A	permission	grants	a	verb.	Scoping	decides	which	rows.	A	supervisor	with	
student.read
	sees	only	students	linked	to	an	active
supervisor_relationship
	for	that	supervisor.	Scoping	runs	as	a	query	filter	in	the	repository,	applied	from	the	principal,	so	it
cannot	be	bypassed	by	a	crafted	request.
12.4	Audit
Every	state	change	writes	an	
audit_event
	with	actor,	action,	aggregate,	before	and	after	summary,	timestamp,	and	request
id.	Academic	and	funding	decisions	carry	a	rationale.	Audit	rows	are	append	only	and	partitioned	by	month.	Reads	of
sensitive	data	can	also	be	audited	where	policy	requires.

13.1	Read	path	separation

16.	Scalability	and	performance	strategy
Stateless	API	pods	behind	a	load	balancer.	Scale	out	with	a	horizontal	pod	autoscaler	on	CPU	and	request	latency.
Connection	pooling	through	PgBouncer	so	many	pods	share	a	bounded	set	of	database	connections.
Read	replicas	absorb	reporting	and	dashboard	load.	The	application	routes	reads	that	tolerate	slight	lag	to	replicas.
Caching	in	Redis	for	reference	data	and	for	
GET	/ api/ v1/ me
	role	resolution,	with	short	time	to	live	and	event	based
invalidation.
Async	workers	absorb	spikes	of	notifications,	milestone	generation,	and	integration	traffic,	so	the	request	path	stays
fast.
Append	heavy	tables	partitioned	by	month	to	keep	indexes	small	and	vacuum	cheap.
Materialized	views	and	scheduled	refresh	keep	expensive	cross	entity	queries	off	the	hot	path.
Backpressure	and	rate	limits	at	the	gateway	protect	the	platform	from	a	misbehaving	client	or	integration.
===== PAGE 32 =====
17.	Security	and	compliance
Transport	encrypted	with	TLS.	Data	encrypted	at	rest	at	the	storage	layer.
Least	privilege	everywhere.	Application	database	roles	are	scoped.	Secrets	come	from	a	secret	manager,	never	from
the	repository.
Input	validated	by	Pydantic	at	the	edge.	Output	schemas	prevent	accidental	field	leakage.
Authorization	checked	on	every	request.	Fail	closed.
Personal	data	handled	under	data	protection	rules.	The	person	model	supports	data	subject	requests,	and	audit
shows	who	accessed	sensitive	records.
Dependency	and	container	scanning	run	in	CI.	Images	are	rebuilt	on	base	image	security	updates.
Webhook	endpoints	verify	signatures.	Outbound	integration	uses	mutual	TLS	or	signed	requests	where	the	partner
supports	it.
